## Пункт 3.2. Первичный ОТК-аудит загруженного массива: методы .info(), .describe(), .memory_usage(). Оценка физического веса таблицы в RAM.

Мы переходим ко второму верстаку третьего блока. Ты открыл шлюзы, и данные зашли в оперативную память. Прямо сейчас перед тобой лежит «черный ящик» — объект `DataFrame`. Прежде чем пускать его дальше по конвейеру трансформации и расчетов, ты обязан мгновенно провести его **первичный ОТК-аудит**. 

Ты должен за одну секунду вскрыть этот массив, увидеть скрытые дефекты типов данных, оценить реальный масштаб пропусков и измерить физический вес таблицы в RAM до последнего байта [91.24].

Положим на верстак три главных диагностических сканера аналитика данных.

---

### АНАТОМИЯ ИНСТРУМЕНТОВ ДИАГНОСТИКИ: ОТК-СКАНЕРЫ

В Pandas есть три встроенных инструмента глубокого сканирования структуры, которые выгружают сухую и плотную спецификацию таблицы прямо в консоль.

#### 1. Сканер №1: Метод `.info()` (Рентген структуры и типов)
Это твой первый и самый главный диагностический инструмент. Он показывает общую архитектуру загруженной матрицы.

```python
df.info(memory_usage="deep")
```
*   **Физика работы в RAM:** Он опрашивает словарь колонок `DataFrame` и выводит:
    *   Общее количество строк (`RangeIndex`).
    *   Список всех столбцов с их точными типами данных (`Data columns / dtypes`).
    *   **Контур пустоты (`Non-Null Count`):** Количество реально заполненных (не-пустых) ячеек в каждом столбце. Если в таблице 10 000 строк, а в столбце `fact_date` метод показывает `8500 non-null`, ты мгновенно, без всяких циклов видишь скрытую брешь — 1500 пропусков, которые нужно будет «заплатить» перед расчетом [91.24].
    *   **Физический вес:** Строка `memory_usage: ...` показывает реальный объем RAM, который занимает таблица. По умолчанию Pandas оценивает вес поверхностно. Флаг `memory_usage="deep"` принуждает алгоритм спуститься на самый глубокий уровень памяти, пройти по всем текстовым ссылкам типа `object` и выдать честный вес до последнего байта.

#### 2. Сканер №2: Метод `.memory_usage()` (Побайтовый весовой контроль)
Если метод `.info()` дает общую картину, то `.memory_usage(deep=True)` работает как точечные весы для каждого отдельного «прута» (столбца) твоей таблицы.

```python
# Возвращает Series, где индекс — имя колонки, а значение — её вес в байтах
print(df.memory_usage(deep=True))
```
*   **Физика в RAM:** Метод выгружает точный физический объем памяти, занятый каждым вектором NumPy. Если ты видишь, что числовой столбец `material_id` весит 80 Кб, а текстовый столбец `status` при том же количестве строк сожрал 5 Мб — это сигнал к оптимизации: текст занимает слишком много места, и его нужно сжимать.

#### 3. Сканер №3: Метод `.describe()` (Математический срез и детекция аномалий)
Этот инструмент проводит моментальный статистический аудит значений внутри колонок.

```python
df.describe(include="all")
```
*   **Физика работы:** Для числовых столбцов он мгновенно рассчитывает: `count` (количество заполненных ячеек), `mean` (среднее значение), `min` (абсолютный минимум), `max` (абсолютный максимум) и квантили.
*   **Зачем это инженеру ПТО:** Ты загрузил сметный реестр и смотришь на строку `min` и `max` в столбце объемов. Если `min` показывает отрицательное число (например, `-150м3`), или `max` выдает неадекватную космическую цифру — ты мгновенно, без ручного пролистывания 3000 строк, ловишь **аномалию грязного ввода** (косяк оператора, который влепил лишний ноль или дефис) [91.24].

### ЗЕРКАЛО SQL

Методы первичного ОТК-аудита в Pandas — это зеркальное отражение запросов к **системному каталогу СУБД (Information Schema)** и базовых агрегатов.
*   Метод `df.info()` — это аналог команды:
    ```sql
    -- PostgreSQL: Проверка структуры таблицы, типов полей и ограничений
    SELECT column_name, data_type FROM information_schema.columns WHERE table_name = 'supply_logs';
    ```
*   Метод `df.describe()` — это пачка параллельных агрегатных функций, запущенных по всем колонкам за один проход:
    ```sql
    SELECT COUNT(quantity), AVG(quantity), MIN(quantity), MAX(quantity) FROM supply_logs;
    ```

### ДЕФЕКТЫ И КАПКАНЫ ГРЯЗНОГО ВВОДА (ОТК-КОНТРОЛЬ)

1.  **Капкан «Скрытого раздувания памяти» типами `object`:**
    Если при вызове `df.info(memory_usage="deep")` ты видишь, что колонка, которая должна быть строго числовой (например, `total_cost`), имеет тип `object` — это авария.
    *   *В чем дефект:* Внутри этой колонки среди миллионов чисел затесалась хотя бы одна мусорная текстовая строка (например, пробел `" "` или слово `"нет"`). Pandas был вынужден перевести весь вектор в тип `object`. Таблица раздулась в памяти в несколько раз [91.24].
    *   *Инструмент защиты:* Немедленно остановить конвейер, найти строку-виновник через фильтрацию и принудительно перевести колонку в числовой тип через `.astype()` или `pd.to_numeric()`, выжигая мусор.
