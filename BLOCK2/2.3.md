# БЛОК 2. ФУНДАМЕНТ PANDAS: СТРУКТУРЫ SERIES И DATAFRAME
## Пункт 2.3. Инструменты навигации: Хирургический срез данных через .loc[] (по меткам) и .iloc[] (по физическим индексам). Капкан SettingWithCopyWarning (почему Pandas ругается при записи в копию таблицы).

Мы переходим к финальному верстаку второго блока. Здесь мы разберем прецизионные инструменты навигации, которые позволяют вырезать любой фрагмент данных из таблицы с точностью хирургического скальпеля, а также полностью ликвидируем главный ментальный кошмар всех аналитиков — предупреждение `SettingWithCopyWarning`.

Положим эти механизмы в коробку, разобрав физику их поведения в RAM.

### ИНСТРУМЕНТ №1: НАВИГАЦИОННЫЕ СКАНЕРЫ — .LOC[] VS .ILOC[]

Забудь про обращение к таблице через двойные квадратные скобки типа `df["volume"][0]`. Это кустарный подход, который заставляет Pandas делать двойную работу в памяти и плодить ошибки. Для извлечения данных существуют два жестких, стандартизированных оператора-индексатора: `.loc[]` и `.iloc[]`.

Оба они работают по единой незыблемой геометрии: **`df.оператор[строки, столбцы]`** — сначала всегда указывается координата строки, затем через запятую координата столбца.

#### 1. Физика оператора `.loc[]` (Навигация по МЕТКАМ)
Оператор `.loc[]` — это текстовый сканер. Он ищет данные по реальному имени (метке) строкового индекса и названию столбца.
```python
# Извлечь объем для конкретного стыка
volume = df.loc["стык_408", "quantity"]
```
* **Физика в RAM:** Под капотом срабатывает логика хэш-таблицы (как в словарях) [91.24]. Pandas берет строку `"стык_408"`, вычисляет её хэш, мгновенно находит физический адрес строки в памяти, а затем по ключу `"quantity"` забирает значение из соответствующего вектора [91.24].
* **Особенность срезов:** Если ты делаешь срез меток через двоеточие `df.loc["стык_01":"стык_03"]`, в результат **включаются обе границы** (и начало, и конец).

#### 2. Физика оператора `.iloc[]` (Навигация по ИНДЕКСАМ)
Оператор `.iloc[]` (Integer Loc) — это числовой сканер. Ему абсолютно плевать, как называются твои стыки и столбцы. Он видит таблицу как чистую физическую матрицу целых чисел, где строки и колонки пронумерованы строго от нуля до конца.
```python
# Извлечь значение из самой первой ячейки (строка 0, колонка 0)
value = df.iloc[0, 0]
```
* **Физика в RAM:** Это самый быстрый способ доступа. Процессор берет базовый адрес начала массива в памяти, умножает смещение на шаг индексов и мгновенно прыгает на нужный физический байт [91.24]. Ему не нужно тратить такты на вычисление хэшей и поиск по строкам.
* **Особенность срезов:** Числовой срез `df.iloc[0:3]` работает по классическому закону Python — **правая граница исключается** (в выборку зайдут только строки 0, 1 и 2).

#### 3. Зеркало SQL
В реляционных базах данных эти операторы отражают логику работы **индексов СУБД**.
* Использование `.loc[]` по уникальному текстовому индексу — это `SELECT ... WHERE primary_key = 'стык_408'`. СУБД использует B-Tree или Hash-индекс для точечного поиска.
* Использование `.iloc[]` — это низкоуровневое обращение к физическому смещению строки на диске (в PostgreSQL это называется системным столбцом `ctid`, хранящим физический адрес страницы и индекс строки внутри неё).

### ИНСТРУМЕНТ №2: БЛОКИРОВКА КАПКАНА SETTINGWITHCOPYWARNING

Каждый инженер данных проходил через этот баг: ты пытаешься изменить значение в таблице, код вроде бы работает, но Pandas выплёвывает в консоль огромное пугающее предупреждение: `SettingWithCopyWarning: A value is trying to be set on a copy of a slice from a DataFrame`.

#### 1. Физика дефекта (Цепочечная индексация)
Этот капкан срабатывает, когда ты пытаешься изменить данные через последовательные (цепочечные) скобки:
```python
# СМЕРТЕЛЬНЫЙ КАПКАН В RAM
df[df["status"] == "verified"]["quantity"] = 0
```
Что происходит внутри оперативной памяти компьютера? 
1. Первыми скобками `df[df["status"] == "verified"]` Pandas вырезает кусок таблицы. Чтобы сэкономить RAM, он часто создает не новую физическую таблицу, а **`View` (Представление/Ссылку)** на кусок старой памяти.
2. Вторыми скобками `["quantity"] = 0` ты приказываешь записать туда ноль.
3. **Системный тупик:** Парсер Pandas зависает, потому что он физически не может гарантировать, куда запишется этот ноль — изменит ли он исходную генеральную таблицу `df`, или затрет временную копию в RAM, которая через секунду сотрется из памяти. Чтобы защитить твой пайплайн от бесшумной порчи данных, система выбрасывает флаг тревоги.

#### 2. Инструмент защиты (Стерильный код)
Чтобы раз и навсегда заблокировать этот капкан, уложи в свою коробку два железных правила:

*   **Правило А. Изменение через единый `.loc` (Запись в исходную матрицу)**
    Никогда не разделяй фильтрацию и выбор столбца на две скобки. Делай это внутри одного оператора `.loc[]` через запятую. В таком случае Pandas точно знает физический адрес ячейки в исходной памяти и меняет её без создания промежуточных копий:
    ```python
    # Безупречная модификация генеральной таблицы
    df.loc[df["status"] == "verified", "quantity"] = 0
    ```

*   **Правило Б. Явное физическое копирование через `.copy()`**
    Если тебе действительно нужен изолированный кусок таблицы для отдельных расчетов (например, отдельная выборка по дефектам), принудительно разорви связь с родительским датафреймом. Создай для него **независимый физический блок ячеек в RAM**:
    ```python
    # Создан абсолютно новый, чистый массив в памяти
    defects_df = df.loc[df["status"] == "defect"].copy()
    defects_df["repair_priority"] = 1  # Никаких ворнингов, контур изолирован
    ```

### КРАТКИЙ ИНВЕНТАРНЫЙ ИТОГ ДЛЯ ТВОЕЙ КОРОБКИ:
* **`.loc[строки, столбцы]`** — вырезает данные по именам и меткам. Правая граница среза всегда включена.
* **`.iloc[строки, столбцы]`** — вырезает данные по физическим номерам ячеек (быстрее, без хэшей). Правая граница исключается.
* **`SettingWithCopyWarning`** — признак цепочечной индексации (двойных скобок). Лечится переводом логики на единый оператор `.loc[фильтр, колонка] = значение` или принудительным созданием изолированной копии через `.copy()`.
