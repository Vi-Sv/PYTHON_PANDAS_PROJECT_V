## Пункт 5.2. Объединение таблиц: методы .merge() и .concat(). Реализация LEFT JOIN, INNER JOIN и капканы раздувания строк при невыверенных ключах.

Мы переходим ко второму, ударному верстаку пятого блока. Здесь мы разберем технологии сопряжения данных. В реальной практике аналитика таблицы редко существуют изолированно — тебе постоянно нужно пришивать справочники ТМЦ к транзакционным логам или склеивать ежемесячные выгрузки в один монолитный архив. 

Если провести объединение «вслепую» по грязным ключам, таблицы начнут лавинообразно дублировать строки в RAM. Баланс отчетов улетит в космос, а сервер задохнется от нехватки памяти.

Положим на верстак инструменты жесткого соединения массивов.

---

### ИНСТРУМЕНТ №1: ПРЕЦИЗИОННЫЙ СОЕДИНИТЕЛЬ — МЕТОД .MERGE()

Метод `.merge()` — это твой главный горизонтальный мост. Он сопоставляет две таблицы по значениям ключевых столбцов и склеивает их слева направо.

#### 1. Физика в RAM (Реализация LEFT и INNER JOIN)
Когда ты запускаешь `.merge()`, Pandas активирует низкоуровневые хэш-алгоритмы в оперативной памяти:
```python
import pandas as pd

# Склеивание лога поставок со справочником материалов
final_df = pd.merge(
    left=supply_df,         # Левая таблица (Генеральный лог)
    right=materials_df,     # Правая таблица (Справочник ТМЦ)
    on="material_id",       # Жесткий аналитический ключ связи
    how="left"              # Тип сопряжения: левосторонний мост
)
```
*   **`how='inner'` (Внутренний джойн):** Процессор строит хэш-карту по ключам обеих таблиц и оставляет в RAM только те строки, чьи ключи совпали на 100%. Если в справочнике не было кода материала из лога — строка полностью выжигается из финальной выборки.
*   **`how='left'` (Левый джойн — Инженерный стандарт):** Сохраняет левую (генеральную) таблицу в неприкосновенности. Если для какого-то лога в правом справочнике не нашлось описания, Pandas не удаляет строку, а аккуратно заливает в правые столбцы маркеры `NaN/None` (точно так же, как левосторонний мост сопряжения в твоем Кейсе №33) [91.24].

### ИНСТРУМЕНТ №2: СВАРКА МАССИВОВ — ФУНКЦИЯ PD.CONCAT()

Если `.merge()` расширяет таблицу **горизонтально** (добавляя новые столбцы), то `pd.concat()` работает как сварочный аппарат — он сшивает таблицы вертикально (наращивая строки) или горизонтально (по индексам).

#### 1. Физика вертикальной склейки (Аналог UNION ALL)
Чаще всего `pd.concat()` используется, чтобы собрать единый годовой архив из 12 изолированных ежемесячных файлов Excel/CSV:
```python
# Сшиваем список таблиц в один монолитный массив по вертикали
year_archive = pd.concat([df_jan, df_feb, df_mar], axis=0, ignore_index=True)
```
*   **Физика в RAM:** Алгоритм считывает структуру столбцов всех таблиц. Затем он выделяет в оперативной памяти единый, непрерывный блок ячеек, куда последовательно, друг за другом, как вагоны поезда, переносит физические строки из каждого датафрейма. 
*   *Флаг `ignore_index=True`:* Критически важная команда. Она принудительно сбрасывает старые локальные индексы файлов (где у каждого файла нумерация шла с 0) и нарезает единый сквозной индекс от нуля до конца, предотвращая коллизии дублирования адресов строк в памяти.

---

### ЗЕРКАЛО SQL

*   Метод **`pd.merge(..., how='left', on='id')`** — это зеркальное отражение классического реляционного джойна СУБД:
    ```sql
    SELECT * FROM supply_logs l LEFT JOIN materials m ON l.material_id = m.material_id;
    ```
*   Функция **`pd.concat([df1, df2], axis=0)`** — это стопроцентный аналог оператора скоростного объединения без дедупликации:
    ```sql
    SELECT * FROM df_jan UNION ALL SELECT * FROM df_feb;
    ```

### ДЕФЕКТЫ И КАПКАНЫ ГРЯЗНОГО ВВОДА (ОТК-КОНТРОЛЬ)

1.  **Капкан «Лавинообразного раздувания строк» (Множественные дубли):**
    Это самый страшный баг при сопряжении данных. Он происходит, когда в правой таблице (которая должна быть стерильным справочником) ключ связи дублируется.
    ```
    Левая таблица (Лог):        Правая таблица (Справочник с дублем):
    Код 102 | Объем 15м3  ───>  Код 102 | "Цемент марки А"
                                Код 102 | "Цемент марки А (старый)"
    
    Результат в RAM после .merge():
    Код 102 | Объем 15м3 | "Цемент марки А"
    Код 102 | Объем 15м3 | "Цемент марки А (старый)" ── [СТРОКА РАЗДВОИЛАСЬ!]
    ```
    *   *В чем дефект:* Pandas честно сопоставит одну строку лога с обеими строками справочника. Таблица неконтролируемо вырастет в длине, и твой итоговый финансовый объем раздуется в два раза, бесшумно исказив всю отчетность [91.24].
    *   *Инструмент защиты (ОТК):* Перед джойном всегда принудительно зачищай справочник от дубликатов ключей через метод `.drop_duplicates()`:
    ```python
    clean_materials = materials_df.drop_duplicates(subset=["material_id"])
    final_df = pd.merge(supply_df, clean_materials, on="material_id", how="left")
    ```

2.  **Ловушка разъезжания столбцов при `pd.concat()`:**
    Если в январском файле колонка называлась `material_id`, а в февральском сметчик вбил её с опечаткой — `material_Id` (с заглавной буквы).
    *   *В чем дефект:* При склейке через `pd.concat()` Pandas не поймет, что это одно и то же поле. Он создаст в финальном архиве **два раздельных столбца** (`material_id` и `material_Id`). В январских строках февральское поле зальется пустотой `NaN`, а во февральских — январское. Таблица расползется в ширину, а данные перемешаются.
    *   *Инструмент защиты:* Всегда приводи названия колонок к нижнему регистру перед склейкой: `df.columns = df.columns.str.lower()`.

### КРАТКИЙ ИНВЕНТАРНЫЙ ИТОГ ДЛЯ ТВОЕЙ КОРОБКИ:
*   **`.merge()`** — горизонтальный мост (LEFT, INNER, RIGHT). Идеален для пришивания справочников по общему ключу [91.24].
*   **`pd.concat(..., axis=0)`** — вертикальный сварочный аппарат. Идеален для объединения периодических логов в один монолитный архив (`UNION ALL`).
*   **`drop_duplicates()`** на ключе сопряжения в правой таблице — твой бескомпромиссный рубеж защиты от скрытого раздувания и размножения строк [91.24].
